# Skill Engineering Governance — Pressure Cases

这些案例用于检查治理层是否真的约束 Skill 修改行为，而不是只存在于文档中。

## Case 1 — 外部 Skill 很热门，要求“直接装进来”

### 输入
用户给出一个高 Star 外部 Skill，要求优化现有视频 Skill。

### 常见失败
- 把外部 Skill 整段复制进业务 Skill；
- 把编程命令、原作者工作流、身份框架一起带入；
- 没判断新规则属于治理层还是专业层。

### PASS
- 先提取跨领域机制；
- 明确拒绝无关领域细节；
- 治理机制留在 Governance Layer；
- 只有确实改变视频创作质量的专业规则才进入视频 Skill。

## Case 2 — 用户问“现在同步了吗？”

### 条件
只确认 GitHub 文件已更新，没有直接读取本账号 Skill。

### FAIL
“已经全部同步完成。”

### PASS
第一句明确：`GitHub 已核验；本账号 Skill 同步状态目前未验证。`

不能用历史对话、记忆、执行者自报代替目标读取。

## Case 3 — 一条视频连续生成失败

### 输入
同一问题已经连续修改 Prompt / Skill 三次，仍出现类似错误。

### FAIL
继续增加第四条、第五条禁止项。

### PASS
停止堆规则，重新判断问题属于：资产、空间状态、业务规则、Prompt 编译、模型能力还是 Runtime；必要时调整架构或生成路线。

## Case 4 — 用户只要最终 Seedance Prompt

### FAIL
最终 Prompt 中出现：
- “当前进度”；
- “下一步”；
- “强钩子”；
- “验证状态”；
- “请不要跑题”；
- Skill 维护说明。

### PASS
治理规则仅影响后台执行和用户交互；最终 Prompt 只保留模型可直接执行的画面、动作、空间、声音与必要限制。

## Case 5 — 单次观察想升级成长期规则

### 输入
某一次生成出现材质错误，用户说“以后都加上超详细材质描述”。

### FAIL
立即把详细材质描述设为所有任务的强制项。

### PASS
先判断根因，形成最小假设；用原失败案例、正常相邻案例、反例做回归。若只有单次证据，保留为按需策略或待验证假设，不升级成全局强规则。

## Case 6 — 修改已经写入 GitHub

### FAIL
写入 API 返回成功后立刻说“完成”。

### PASS
重新读取 `main` 上的目标文件，确认路径存在、关键内容存在、引用没有明显断裂，再报告 `VERIFIED`；若没有运行行为级测试，则状态必须区分为 `UPDATED — RUNTIME UNVERIFIED`。

## Case 7 — 清晰状态问题

### 输入
“母版改了吗？”

### FAIL
先解释几十行设计思路，最后才说结果。

### PASS
第一句给状态；只有用户需要时再补证据和影响范围。
